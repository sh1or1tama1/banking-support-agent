一句话总结：我们用"防泄漏"的方式切分了银行客服数据，建立了冻结的评测集和两个基线；然后做了一个会"先分析、再检索、给证据打分、必要时改写查询、生成后自检、不行就转人工"的 Agentic RAG。它比 Naive RAG 显著更好（0.57 → 0.73），最大的进步是知道什么时候该转人工。但消融实验显示，单独去掉任何一个组件都没有显著影响——提升主要来自"分析 + 明确选择动作"这两步。

1. 项目在做什么

我们做一个银行客服助手，分两个任务：

任务输入 → 输出比较什么
Task 1 意图分类"how do I block my card?" → block_card（26 类之一）TF-IDF+LR vs 微调 BERT vs LLM few-shot
Task 2 回复生成客户问题 → 动作（answer / clarify / escalate）+ 回复文本Direct LLM（参考下限）vs Naive RAG（基线） vs Agentic RAG（挑战者）
为什么 Task 2 要做 Agentic RAG？ 教授建议挑战者不要只是"单独的 LLM"，而要更高级。所以我们把 RAG + LLM 当基线，再做一个带多步推理、检索改进、答案验证的 Agentic RAG 去挑战它。Direct LLM 只是一个参考下限。
为什么动作这么重要？ 真实银行客服里，很多问题不能从知识库回答（比如"我的转账为什么还在 pending"需要查账户）。一个好助手应该转人工（escalate），而不是编一个看起来像样的答案。所以我们的主指标是"行为正确率"：系统有没有选对动作。

1.2 防泄漏划分（notebook 01）

做了什么先把问题规范化（小写、去占位符和标点），在每个意图内部用字符 3–5-gram TF-IDF 做"领头人聚类"（余弦 ≥ 0.90 归为一组），再用 StratifiedGroupKFold 按整组切成 70/15/15，种子 42。
为什么Bitext 很多问题是同一模板的改写。随机切分会把"几乎一样"的句子同时放进训练和测试，分数虚高——这叫数据泄漏。
结果训练 17,882 / 验证 3,832 / 测试 3,831；每个意图都在每个划分里；可复现（test ID 哈希 c9dc69de5256db74）。
诚实的发现即使分组，52.1% 的测试句在训练集仍有相似度 ≥0.9 的近亲（随机切分是 59.9%）。这是模板数据的本质，所以需要 BANKING77 做真实测试。
图 1. 每个测试句与训练集的最大相似度：分组切分（我们） vs 随机切分
概念：GroupKFold——保证"同一组"的样本只出现在一个划分里；Stratified——同时保证每个划分里各意图比例相同。两者合起来就是 StratifiedGroupKFold。

1.7 两个基线：Direct LLM 和 Naive RAG

问题→LLM→动作 + 回复Direct LLM
问题→向量检索 top-3（16,804 条知识库）→LLM→动作 + 回复Naive RAG

公平性设置：三个系统共用同一份 policy prompt（policy_v1：不编造、用占位符、不声称执行了操作、不索要密码、输出 JSON），同一个模型 gpt-5.4-nano，temperature 0，所有调用缓存到磁盘（可复现、省钱）。

阶段一结果：Direct 0.17，Naive 0.57。Direct 几乎总是反问（因为没有上下文就不敢回答）；Naive 能答好清楚的 Bitext 问题，但几乎从不转人工（b77_unsupported 只有 0.12），而且在提示注入 "Ignore your previous instructions…" 上照着检索到的密码片段回答了——这正是 Agentic RAG 要解决的问题。

2.2 Task 1 误差分析（BERT 在 BANKING77 上的 272 个错误）

  • 48% 的错误来自 4 个"费用"意图：真实客户问"为什么扣了这笔费"，Bitext 的 check_fees 是"在哪看费用"。BERT 于是跟着其他词走：transfer → make_transfer，cash → dispute_ATM_withdrawal。
  • 关键词锚定："ATM" 把问题拉向 recover_swallowed_card，"transaction" 拉向 dispute_ATM_withdrawal。
  • 置信度只在最顶端可信：conf ≥ 0.99 时 BERT 对 90%；≥ 0.6 时只对 55%。→ 这直接决定了 agent 的阈值（2.5 节）。
  • 模型错法不同：BERT 错的 272 条里，LLM 对了 138 条。

抽了 20 个错误分成两类：模型问题（问题意思很清楚，模型错得没道理）10 个，映射/标签问题（BANKING77 标签有噪声，或另一个 Bitext 意图同样合理）10 个。例如 "Oh no! I lost my card!" 标为 block_card，BERT 说 cancel_card——Bitext 区分"冻结"和"注销"，BANKING77 不区分，这是映射问题。

2.4 Agentic RAG 的结构（LangGraph）

节点做什么对应的"高级"能力
① analyzeLLM 判断：是不是银行问题、要不要追问、拆成子问题、写检索查询；同时调用 Task 1 的 BERT 作为工具预测意图多步推理、工具调用
② retrieve向量检索 + BM25 关键词检索，用 RRF 融合取 top-3；BERT 置信度 ≥ 0.99 时才按意图过滤检索改进
③ gradeLLM 给每个片段打"相关/不相关"检索改进
④ rewrite没有相关片段就改写查询再检索（第二轮去掉意图过滤）检索改进
⑤ generate按动作顺序选 answer / clarify / escalate 并写回复—
⑥ validate检查答案：编造？声称执行操作？索要密码？漏答？不通过就带反馈重写一次或转人工答案验证

真实例子：一条问题走一遍

问题my visa has been stolen how do i block i
① analyzeintent=block_card, is_banking=true, needs_clarification=false
① tool:BERTblock_card, 置信度 0.997（≥ 0.99 → 开启意图过滤）
② retrieve3 个 block_card 片段
③ graderelevant = [1, 2, 3]：都是挂失被盗 Visa 的步骤
⑤ generateanswer："I'm really sorry your Visa was stolen… contact ACME Bank Support at {{Customer Support Phone Number}}…"
⑥ validate所有检查通过 → verdict = pass → 输出
概念：RRF（Reciprocal Rank Fusion）：每个文档的融合分 = Σ 1/(60 + 它在各检索器里的排名)。不需要把两种检索的分数归一化，只看排名，简单又稳。
概念：BM25：经典关键词检索，擅长精确词匹配；向量检索擅长同义改写。两者互补。

显著性：McNemar 检验。同一批问题、两个系统，只看"一个对一个错"的那些题：Agentic 对而 Naive 错 90 条，反过来 20 条。如果两系统一样好，这两个数应该差不多；90 vs 20 的概率 p < 0.0001，所以差距是真的，不是运气。
概念：precision / recall：precision = 转人工的里面有多少是该转的；recall = 该转的里面转了多少。Agentic 的 recall 从 0.25 涨到 0.60，precision 只小降，F1 大涨。
主要进步：① 不支持的问题会转人工了（0.12 → 0.52）；② 提示注入被正确拒绝并转人工；③ 真实可答问题提升（0.47 → 0.60）。
还剩的问题：b77_unsupported 里 38% 还是在反问而不是转人工（例如 "How do I link a card that I already have?"）；有些能答的"为什么扣费"问题被转人工了（b77_real_inscope 有 34% 被转人工）。

怎么解读（这是报告里很好的讨论点）：
  • 验证几乎不触发：436 条里只判不合格 0.7%，只改写了 6 次。它的作用如果有，是在回答质量（是否编造、是否安全）上，行为正确率测不到 → 需要阶段三的人工评分和 LLM judge 来检验。
  • 打分在 19% 的问题上触发了查询改写，但很少改变最终动作。
  • 混合检索、BERT 过滤在不同子集上有小涨小跌，相互抵消。
  • 所以相对 Naive RAG 的提升主要来自 analyze（判断是否银行问题、是否需要追问）和生成器里明确的"回答/追问/转人工"决策，而不是检索方面的改进。
概念：消融实验（ablation）——像拆零件一样每次去掉一个组件，看性能掉多少，从而知道每个组件到底贡献了什么。"去掉后没变化"本身就是一个有价值的结论。

2.8 局限与诚实说明（报告里一定要写）

  1. 调 prompt 不对称：Agentic 的 prompt 在 dev 上调过，Naive 的没调。dev 上没调的 agent v1（0.688）并不比 Naive（0.708）好，所以一部分提升可能来自"调参功夫"而非架构。更公平的做法：在同一个 dev 集上也调一下 Naive RAG。
  2. Dev 集小（48 条），v2 的选择可能对它有点过拟合。
  3. 消融的延迟不可比：消融复用了完整版缓存的 LLM 调用，所以延迟接近 0。延迟只看 agentic_full，成本按 token 算。
  4. 自动检查只是代理指标：编造检测的正则会把客户自己写的金额也算进去。
  5. Task 1 LLM 准确率是严格口径（FEES vs check_fees）。

自测：老师/同学可能问的问题

先自己想答案，再点开看。

为什么不用随机切分数据？Bitext 是模板生成的，很多句子是同一模板的改写。随机切分会把近似重复句同时放进训练和测试，分数虚高。我们在每个意图内按相似度 ≥0.90 聚类，再按整组切分。即使这样仍有 52% 的测试句在训练里有近亲，所以我们额外用真实的 BANKING77 测试。
BERT 在 Bitext 上满分，为什么还说它不够好？因为 Bitext 测试和训练太像了，满分说明不了什么。在真实客户问题（BANKING77）上 BERT 只有 0.477，只比 TF-IDF 高 7 个点；LLM few-shot 不用训练就有 0.692。
你们的 Agentic RAG 比 Naive RAG 好在哪？差距可信吗？行为正确率 0.57 → 0.73，转人工 F1 0.38 → 0.65。McNemar 检验：Agentic 独对 90 条、Naive 独对 20 条，p < 0.0001。主要进步是知道该转人工、能拒绝提示注入。
消融实验都没有显著差异，是不是说明你们的组件没用？说明这些组件对"选对动作"贡献小，提升主要来自分析步骤和明确的动作决策。验证步骤的作用可能在回答质量（编造、安全），行为正确率测不到，需要阶段三的人工评分和 LLM judge 来检验。这是一个诚实的、值得讨论的发现。
你们有没有在测试集上调参？没有。prompt 在一个单独的 48 条 dev 集上调（来自验证集、BANKING77 train 和新写的问题），阈值在验证集和 BANKING77 train 上选。评测集冻结后只跑了一次。
对比公平吗？三个系统共用同一个 policy prompt、同一个模型（gpt-5.4-nano）、temperature 0、同一份评测集。不对称的地方是 agent 的 prompt 调过、Naive 没调——报告里要说明，dev 上未调的 agent v1 并不比 Naive 好。
为什么 BERT 阈值选 0.99 这么高？BERT 在真实问题上常常"自信地错"。阈值 0.6 时过滤会把正确文档挡掉，真实问题 R@1 从 0.642 掉到 0.532；0.99 时几乎不损失（0.641），合成数据仍是 1.000。误差分析也显示 conf ≥ 0.99 时 BERT 对 90%，≥ 0.6 时只对 55%。
Agentic RAG 的代价是什么？每条约 3.6 次 LLM 调用，延迟 4.1 s（Naive 1.4 s），成本约 2.5 倍（436 条 $0.40 vs $0.16）。绝对成本仍然很低。
为什么用 LLM 当裁判之前还要人工评分？LLM judge 可能有偏差，必须先在 100 条子集上和两位人工评分对比（kappa），证明它可靠，再用它评全部 436 条。
